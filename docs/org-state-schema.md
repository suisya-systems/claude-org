# org-state.json Schema Definition

> **Status: historical / pre-M4** (as synced with Issue #353)
>
> The descriptions in this document about the "Source of truth rules", "Markdown is canonical", and "rerun the converter" reflect the **pre-M4 cutover model** and are no longer consistent with the current implementation. **The current canonical reference is [`docs/contracts/state-semantics-contract.md`](contracts/state-semantics-contract.md):**
>
> - `.state/state.db` is the **single SoT** for `runs` / `org_sessions` / `worker_dirs` / `events`.
> - `.state/org-state.md` is a **derived artifact** that the `StateWriter.transaction()` post-commit hook regenerates automatically via `tools/state_db.snapshotter` (manual edits are drift).
> - `.state/org-state.json` is also a derived artifact, generated by `dashboard/org_state_converter.py`, which now reads state.db directly (the `--source markdown` mode was removed at M4).
> - The legacy "manually edit `org-state.md` → rerun the converter" loop **must not be used**. Writes to state.db go through the `tools/state_db.writer.StateWriter` API (`upsert_run` / `update_run_status` / others).
>
> The JSON schema definition (version 1) retained below is kept as a migration-only reference so the dashboard and external consumers can look up the payload shape. If a field's meaning conflicts with state-semantics-contract, the contract governs.

## Overview

`.state/org-state.json` is a derived JSON snapshot generated from state.db by `dashboard/org_state_converter.py`.
**Since M4, the dashboard itself (`dashboard/server.py`) reads state.db directly and does not consult this file.** The JSON remains as a derived snapshot for external consumers (CI / external scripts / readers in other languages, etc.).

### Regenerating the JSON (reference)

As long as writes to state.db go through `StateWriter.transaction()`, the post-commit hook regenerates **(a) `.state/org-state.md` via `tools/state_db.snapshotter`** and **(b) `.state/org-state.json` via `dashboard.org_state_converter.convert()`** as separate hooks, so manual regeneration is normally unnecessary. To regenerate just the JSON for local debugging:

```bash
py -3 dashboard/org_state_converter.py      # Windows
python3 dashboard/org_state_converter.py     # Mac/Linux
```

### Update points (reference, historical)

The table below describes the pre-M4 "skill edits the markdown → converter produces JSON" flow. **The current SoT is the state.db write**; the corresponding APIs are:

| Operation | Skill / path | Current writer |
|---|---|---|
| Worker dispatch (T1 reservation) | org-delegate | `tools/gen_delegate_payload.py` (`StateWriter.upsert_run` with `runs.status='queued'`) |
| Pane spawn (T2) | dispatcher delegate-plan helper | `StateWriter.upsert_run` with `runs.status='in_use'` |
| Status change (T4 review / T5 completed / T6 review→in_use) | org-delegate / org-pull-request | `StateWriter.update_run_status` |
| Org suspend / resume | org-suspend / org-resume | Updates `org_sessions.status` via `StateWriter` (does not change individual `runs.status`, [contract I4](contracts/state-semantics-contract.md)) |
| Dispatcher / Curator recording | org-start | Updates `org_sessions` dispatcher / curator pane+peer fields via `StateWriter` |

For all these writes, the `StateWriter.transaction()` post-commit hook regenerates derived artifacts separately via the markdown snapshotter (`tools/state_db.snapshotter`) and the JSON converter (`dashboard.org_state_converter.convert()`), so skills do not need to invoke the converter themselves.

## Schema (version 1)

```json
{
  "version": 1,
  "updated": "<ISO 8601 timestamp | null>",
  "status": "ACTIVE | SUSPENDED | IDLE",
  "currentObjective": "<string | null>",
  "workItems": [
    {
      "id": "<kebab-case task ID>",
      "title": "<task title (may be Japanese)>",
      "status": "IN_PROGRESS | REVIEW",
      "progress": "<latest progress note | null>",
      "worker": "<peer ID | null>"
    }
  ],
  "workerDirectoryRegistry": [
    {
      "taskId": "<task ID>",
      "pattern": "A | B | C",
      "directory": "<absolute path>",
      "project": "<projects.slug; ephemeral runs also emit the slug as-is>",
      "status": "<runs.outcome_note OR runs.status — any of the seven values may appear (queued / in_use / review / completed / failed / suspended / abandoned)>"
    }
  ],
  "dispatcher": {
    "peerId": "<renga-peers peer ID>",
    "paneId": "<renga pane ID>"
  },
  "curator": {
    "peerId": "<renga-peers peer ID>",
    "paneId": "<renga pane ID>"
  },
  "resumeInstructions": "<free text | null>"
}
```

## Field descriptions

### Top level

| Field | Type | Description |
|---|---|---|
| `version` | `integer` | Schema version. Currently `1`. Incremented on a future incompatible change |
| `updated` | `string \| null` | Value of the `Updated:` field in org-state.md (ISO 8601). `null` if unset |
| `status` | `string` | Org status. `ACTIVE` (running) / `SUSPENDED` (paused) / `IDLE` (unused) |
| `currentObjective` | `string \| null` | Current objective (the `Current Objective:` field). `null` if unset |
| `workItems` | `array` | List of work items |
| `workerDirectoryRegistry` | `array` | Worker directory reuse table |
| `dispatcher` | `object \| null` | Dispatcher peer / pane information. `null` if not recorded |
| `curator` | `object \| null` | Curator peer / pane information. `null` if not recorded |
| `resumeInstructions` | `string \| null` | Notes for resume time (written by org-suspend). `null` if absent |

### workItems entry

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Task ID (kebab-case English). Examples: `blog-redesign`, `data-analysis` |
| `title` | `string` | Task title (may be Japanese). Taken from the `- {id}: {title} [{status}]` line in org-state.md |
| `status` | `string` | Task status (see below) |
| `progress` | `string \| null` | Latest progress note (the `- result:` sub-item). `null` if absent |
| `worker` | `string \| null` | Peer ID of the assigned worker (the `- worker:` sub-item). `null` if absent |

**status values (current under M4):**

`workItems` is generated by `dashboard/org_state_converter.py` from **active runs only** (`runs.status IN ('in_use','review')`, see `_ACTIVE_STATUSES` in [`tools/state_db/queries.py`](../tools/state_db/queries.py)), so the values that actually appear today are these two:

| Value | Source (`runs.status`) | Meaning |
|---|---|---|
| `IN_PROGRESS` | `in_use` | Working ([contract § 3.2](contracts/state-semantics-contract.md)) |
| `REVIEW` | `review` | Under review (worker has reported completion; awaiting human approval) |

`COMPLETED` / `ABANDONED` / `PENDING` / `BLOCKED` **do not appear in the `workItems` array** (terminal states are excluded from `workItems`, and `PENDING` / `BLOCKED` are not valid `runs.status` values in the DB enum). For the closed seven-value run-status definition, see [`docs/contracts/state-semantics-contract.md` § 2](contracts/state-semantics-contract.md).

### workerDirectoryRegistry entry

| Field | Type | Description |
|---|---|---|
| `taskId` | `string` | Task ID using this directory |
| `pattern` | `string` | Directory pattern: `A` (project directory) / `B` (worktree) / `C` (ephemeral) |
| `directory` | `string` | Absolute path of the worker directory |
| `project` | `string` | `projects.slug` (the project's kebab-case identifier) emitted as-is. Note that this is **not** the `display_name` (the human-facing label). Ephemeral runs are not specialized; the slug is emitted as-is |
| `status` | `string` | If `runs.outcome_note` is set, that value; otherwise `runs.status` projected as-is. `runs.status` is a closed seven-value enum (`queued` / `in_use` / `review` / `completed` / `failed` / `suspended` / `abandoned`), and a `queued` row at the T1 reservation stage will appear in this array as well as long as `worker_dir_id` is bound. The pre-M4 `available` notation is no longer emitted by the implementation. Details in [`dashboard/org_state_converter.py`](../dashboard/org_state_converter.py) |

### dispatcher / curator

| Field | Type | Description |
|---|---|---|
| `peerId` | `string` | Stable peer identifier assigned by renga-peers (set when `assigned`). The value passed to `to_id` of `mcp__renga-peers__send_message`. Example: `peer-dispatcher-001` |
| `paneId` | `string` | renga pane id. An identifier independent of `peerId`, tied to the lifecycle of the pane. Example: `pane-42` |

## Dashboard integration

> **historical**: Before M4, `dashboard/server.py` would read `.state/org-state.json` (if present) first and fall back to `.state/org-state.md`. **Since M4, `dashboard.server.build_state` reads `.state/state.db` directly** and does not consult `org-state.json` / `org-state.md` at all (see the docstring at the top of [`dashboard/server.py`](../dashboard/server.py) and [`docs/contracts/state-semantics-contract.md` § 1.2](contracts/state-semantics-contract.md)). `org-state.json` remains as a derived snapshot for external consumers.
