# org-state.json Schema Definition

## Overview

`.state/org-state.json` is the machine-readable snapshot of `.state/org-state.md`.
It is introduced so the dashboard (`dashboard/server.py`) and other programmatic consumers can prefer loading JSON.

### Source of truth rules

**Markdown is canonical; JSON is derived.**

- `org-state.md` is always the source of truth. Claude Code instances read and write it directly.
- `org-state.json` is a derived file. It is generated by `org_state_converter.py`.
- If you manually edit `org-state.md`, always rerun the converter.
- If the two conflict, trust `org-state.md`.

### Regenerating JSON

```bash
py -3 dashboard/org_state_converter.py      # Windows
python3 dashboard/org_state_converter.py     # Mac/Linux
```

### Update points

After performing any of the following operations, run the converter to update JSON:

| Operation | Skill | Updated content |
|---|---|---|
| Worker dispatch | org-delegate Step 4 | Current Objective, Active Work Items, Worker Directory Registry |
| Status change | org-delegate Step 5 | Work item status (`REVIEW`/`COMPLETED`/`IN_PROGRESS`) |
| Organization suspend | org-suspend Phase 3 | Status=`SUSPENDED`, Updated, Work Items, Resume Instructions |
| Organization resume | org-resume Phase 4 | Status=`ACTIVE` |
| Startup (Dispatcher/Curator record) | org-start Steps 2-3 | Dispatcher/Curator `peerId` / `paneId` |

## Schema (version 1)

```json
{
  "version": 1,
  "updated": "<ISO 8601 timestamp | null>",
  "status": "ACTIVE | SUSPENDED | IDLE",
  "currentObjective": "<string | null>",
  "workItems": [
    {
      "id": "<kebab-case task ID>",
      "title": "<task title (may be Japanese)>",
      "status": "IN_PROGRESS | COMPLETED | PENDING | BLOCKED | REVIEW | ABANDONED",
      "progress": "<latest progress note | null>",
      "worker": "<peer ID | null>"
    }
  ],
  "workerDirectoryRegistry": [
    {
      "taskId": "<task ID>",
      "pattern": "A | B | C",
      "directory": "<absolute path>",
      "project": "<project name | ->",
      "status": "in_use | available"
    }
  ],
  "dispatcher": {
    "peerId": "<renga-peers peer ID>",
    "paneId": "<renga pane ID>"
  },
  "curator": {
    "peerId": "<renga-peers peer ID>",
    "paneId": "<renga pane ID>"
  },
  "resumeInstructions": "<free text | null>"
}
```

## Field descriptions

### Top level

| Field | Type | Description |
|---|---|---|
| `version` | `integer` | Schema version. Currently `1`. Increment on future breaking changes |
| `updated` | `string \| null` | Value of the `Updated:` field in org-state.md (ISO 8601). `null` if unset |
| `status` | `string` | Organization state. `ACTIVE` (running) / `SUSPENDED` (suspended) / `IDLE` (unused) |
| `currentObjective` | `string \| null` | Current objective (`Current Objective:` field). `null` if unset |
| `workItems` | `array` | List of work items |
| `workerDirectoryRegistry` | `array` | Worker directory reuse table |
| `dispatcher` | `object \| null` | Dispatcher peer/pane information. `null` if not recorded |
| `curator` | `object \| null` | Curator peer/pane information. `null` if not recorded |
| `resumeInstructions` | `string \| null` | Notes for resuming (written by org-suspend). `null` if absent |

### workItems entries

| Field | Type | Description |
|---|---|---|
| `id` | `string` | Task ID (English kebab-case). Example: `blog-redesign`, `data-analysis` |
| `title` | `string` | Task title (Japanese allowed). Extracted from `- {id}: {title} [{status}]` in org-state.md |
| `status` | `string` | Task state (see below) |
| `progress` | `string \| null` | Latest progress note (`- 結果:` sub-item). `null` if absent |
| `worker` | `string \| null` | Assigned worker peer ID (`- ワーカー:` sub-item). `null` if absent |

**`status` values:**

| Value | Meaning |
|---|---|
| `IN_PROGRESS` | In progress |
| `COMPLETED` | Completed (approved by a human) |
| `PENDING` | Pending (not started yet) |
| `BLOCKED` | Blocked (dependencies or issues) |
| `REVIEW` | In review (worker has reported completion, waiting for human approval) |
| `ABANDONED` | Abandoned |

### workerDirectoryRegistry entries

| Field | Type | Description |
|---|---|---|
| `taskId` | `string` | Task ID using that directory |
| `pattern` | `string` | Directory pattern: `A` (project directory) / `B` (worktree) / `C` (ephemeral) |
| `directory` | `string` | Absolute path of the worker directory |
| `project` | `string` | Project name. `-` for ephemeral |
| `status` | `string` | `in_use` (active) / `available` (completed and reusable) |

### dispatcher / curator

| Field | Type | Description |
|---|---|---|
| `peerId` | `string` | Stable peer identifier assigned by renga-peers (set when `assigned`). Value passed to `mcp__renga-peers__send_message` as `to_id`. Example: `peer-dispatcher-001` |
| `paneId` | `string` | renga pane ID. Identifier independent from `peerId`, tied to the pane lifecycle. Example: `pane-42` |

## Dashboard integration

`dashboard/server.py` loads org-state with the following priority:

1. If `.state/org-state.json` exists and its mtime is greater than or equal to `.state/org-state.md` -> use JSON
2. Otherwise -> parse `.state/org-state.md` with regular expressions (fallback)

This design keeps the system working even when the converter has not been run or JSON is stale.
